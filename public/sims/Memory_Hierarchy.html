So why does a CPU give up half its silicon for cache?

Because it is trying very hard never to make the long trip. Cache is a small, close copy of whatever the CPU has been using lately. When the guess is right the data is one second away. When it's wrong, it's a hundred.

Slide it from 99% down to 90% — a tiny change in the guess rate, a huge change in the wait.

Why this explains so much. Adding RAM helps because it keeps you off the disk. An SSD felt like a bigger upgrade than a new processor because it cut a four-month trip down to a day. A game stutters when it needs something nobody predicted. And the enormous cache blocks in a CPU floorplan stop looking like wasted space — they are the entire reason the math units ever have anything to work on. Simplified: these are typical round figures; exact latencies vary by chip, and real systems overlap many of these waits rather than sitting idle through each one.

For the curious — the actual numbers

Latencies are usually measured in nanoseconds (ns) — billionths of a second — and microseconds/milliseconds (millionths/thousandths of a second) once you're off-chip:

LocationTypical latency
L1 cache~1 ns
L2 cache~4 ns
L3 cache~15 ns
RAM~100 ns
SSD~100,000 ns (100 µs)
Hard drive~10,000,000 ns (10 ms)
Overseas server~150,000,000 ns (150 ms)

The average-wait number in the cache panel is a weighted average: avg = hitRate × L1time + (1 - hitRate) × RAMtime. At a 95% hit rate with L1 = 1 ns and RAM = 100 ns, that's 0.95 × 1 + 0.05 × 100 = 5.95 ns, which the sim rounds to 6. When programmers say a program is "memory-bound," they mean this average is dominated by RAM misses rather than by the CPU's own math — the fix is usually restructuring data so nearby accesses land in the same cache line.
