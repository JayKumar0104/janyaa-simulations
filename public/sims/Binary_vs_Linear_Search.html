Simplified: assumes the list is already sorted, which is what makes binary search possible at all — searching an unsorted list can't skip ahead like this.

For the curious — why the gap gets worse as the list grows

Linear search has to be prepared to look at every item, so its worst case is N guesses. Binary search halves the range each time, so its worst case is the number of halvings it takes to get from N down to 1 — that is floor(log₂ N) + 1:

Read the last row again: a million numbers costs binary search twice what a thousand costs it. Doubling the length of the list only ever adds one guess. That is the same exponent relationship as folding a sheet of paper — every fold doubles the thickness, so it takes surprisingly few folds to get somewhere absurd — read in the opposite direction: every guess halves the search, so it takes surprisingly few guesses to get down to one answer.

The procedure itself, in full:

lo = 1; hi = N; guess the middle; if too low, lo = middle + 1; if too high, hi = middle − 1; repeat.

What it costs. Binary search only works because the list is sorted — the "higher or lower" answer is what lets it discard a whole half. Sorting a list in the first place is real work, so binary search pays off when you search the same sorted list many times, which is exactly what a dictionary, a phone book, a database index, and a git bisect all are. The same logarithm turns up everywhere a problem is repeatedly cut in half.
